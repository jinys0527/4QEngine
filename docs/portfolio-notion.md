## 핵심 설계 1 — GameManager Phase / TurnState

**턴 루프 일원화**

**문제** — Player와 Enemy가 각자 자기 턴을 끝내고 다음 대상에게 턴을 넘겼다. 평상시엔 돌았지만 **전투 난입**(탐험 중 적과 조우)이나 **층 전환** 같은 흐름 변화가 끼어들면 턴 소유자가 모호해져 루프가 꼬였다. 두 주체가 서로를 직접 호출하니 누가 진행 권한을 가졌는지 코드만 보고 판단할 수 없었다.

**개선** — 턴 진행 권한을 `GameManager` 한 곳으로 모으고, Player·Enemy·UI는 이벤트로만 통신하게 했다.

| 계층 | 흐름 |
| --- | --- |
| **Phase** | GameStart → InitCharacter → ExplorationLoop → CombatTrigger → CombatInit → TurnBasedCombat → CombatEnd → Shop → NextFloor → GameOver |
| **탐험 턴** | PlayerTurn ↔ EnemyStep |
| **전투 턴** | SelectActor → PlayerTurn / EnemyTurn → Resolve |

Phase의 `onEnter`/`onExit`에서 수위 활성화, Player FSM 이벤트 디스패치, 전투 턴 상태 초기화, 층 전환 요청을 수행한다. 탐험과 전투가 각자의 턴 상태를 갖는 이중 구조라, 전투 중에 탐험 턴이 섞여 들어오는 문제가 구조적으로 사라졌다.

**결과** — 전투 난입·층 전환에도 턴 루프가 일관되게 유지된다. 주사위 연출이 끝날 때까지 턴을 대기시키는 등 연출–로직 동기화도 이 지점에서 처리한다.

## 핵심 설계 2 — 데이터 기반 FSM + UI 시스템

**기획자가 직접 고칠 수 있는 구조**

현업 클라이언트 작업의 상당 부분이 "기획이 코드 없이 수정할 수 있게 만드는 일"이라고 생각해서, 플레이어 행동과 UI를 데이터로 빼는 데 시간을 썼다.

### FSM

| 항목 | 내용 |
| --- | --- |
| 데이터화 | 상태 / 전이 / 액션을 JSON으로 직렬화하는 `FSMGraph`, 에디터 Inspector에서 편집 |
| 코드와 데이터의 경계 | Action·Event는 **C++ Registry에 등록된 것만** 에디터에서 선택 가능 → 핵심 로직은 코드, 조합은 데이터 |
| 이벤트 연결 | UI·Collision·Animation 이벤트를 문자열 이벤트로 매핑해 전이 트리거 |
| 상태 폭발 방지 | 메인 FSM + 서브 FSM 6개로 분리 (Combat / Move / Push / Inventory / Shop / Door) |
| 입력 동기화 | UI·입력이 플래그를 세팅하고 FSM 액션 핸들러가 `Consume*` 계열로 소비 후 기본값 복구 |

### UI

| 항목 | 내용 |
| --- | --- |
| 컴포넌트 | 12종 · 7,864줄 — Button / Image / Text / Slider / ProgressBar / NumberSprite / DicePanel / DiceDisplay / DiceRollAnimation / UIFSM / UIComponent / UIObject |
| 전용 셰이더 | `UI_ProgressCircle_PS.hlsl` — 원형 게이지 (턴 종료 버튼의 Arc 게이지) |
| 렌더링 확장 | ProgressBar FillDirection + Arc, 마스크 이미지, 알파 클립 |
| 레이아웃 | HorizontalBox 자동 적용, 부모 기준 Offset 바운드 계산 |
| 상태 관리 | `UIFSMComponent`로 상점·문·ESC 메뉴 상태 전환 |
| 직렬화 | UI를 씬 데이터로 저장 → 에디터에서 배치하면 런타임이 그대로 로드 |

**결과** — 주사위 연출, 선제권 표시, 상점/자판기, 스테이지 UI 등 인게임 UI 전체를 이 프레임워크로 구현했다. 상태 전이와 UI 배치를 코드 수정 없이 데이터로 조정할 수 있다.

**한계** — 에디터의 UI 편집 도구 자체는 배치·복사·삭제 수준에서 멈췄다. 레이아웃 편집기 수준까지는 만들지 못했고, 그래프 에디터·Undo·범용 payload 같은 확장은 일정 안에 돌아가는 편집/저장/로드 흐름을 우선하기 위해 의도적으로 잘라냈다.

## 핵심 설계 3 — 에셋 파이프라인

**툴과 런타임 분리**

Assimp를 런타임에 붙이면 빠르지만 런타임 의존성·로딩 시간·배포 문제가 커진다. 단순 라이브러리 연결이 아니라 **"런타임에 무엇을 남기고 무엇을 툴로 뺄 것인가"**의 결정으로 접근했다.

| 단계 | 내용 |
| --- | --- |
| 1. 임포트 | Editor/Importer만 Assimp 링크 → FBX를 `.meshbin`(magic/version 헤더) + Material/Skeleton/Animation JSON으로 변환 |
| 2. 런타임 | 자체 포맷만 역직렬화, Assimp 코드 없음 |
| 3. 캐시 | `ResourceStore`가 key 기반 캐시 (동일 key → 동일 handle) → GPU 리소스 생성 |

**측정 결과** — 게임에 실제로 쓰이는 202개 에셋 전체 기준

| | FBX 직접 로드 | `.meshbin` | |
| --- | --- | --- | --- |
| 로드 시간 | 765.2 ms | **21.86 ms** | **35.0배** |
| 파일 크기 | 49.5 MB | **32.1 MB** | 0.65배 |

정점 503,924개 / 서브메시 261 / 스키닝 24개 · 배수 분포 최소 7.5배 · 중앙값 25.6배 · 최대 79.0배

느린 이유는 파일 I/O가 아니라 Assimp가 매번 수행하는 후처리(삼각형화, 노멀·탄젠트 계산, 중복 정점 병합, RH→LH 변환)다. 결과가 결정적이므로 실행마다 반복할 이유가 없다.

**런타임 의존성 0** — `Client.exe`(Release) import table을 `dumpbin`으로 확인한 결과 Assimp와 그 전이 의존 6종(`zlib1`, `pugixml`, `poly2tri`, `minizip`, `kubazip`, `draco`)이 하나도 없다. 서드파티 DLL은 `fmod.dll` 단독. 반면 `Editor.exe`는 Assimp에 의존한다.

**안정 참조와 런타임 참조의 분리** — 실행마다 값이 달라지는 `ResourceHandle(id, generation)`은 파일에 저장하지 않는다. 파일에는 key/path만 저장하고, Deserialize 이후 `ResourceStore`가 key를 handle로 복원한다.

## 핵심 설계 4 — 스켈레탈 애니메이션

**포즈부터 GPU 팔레트까지**

`AnimationComponent`(클립 재생·블렌딩·리타겟팅으로 Local Pose 생성)와 `SkeletalMeshComponent`(Global Pose 누적·팔레트 변환)로 책임을 분리했다.

**파이프라인** — Playback(시간·루프·normalized time) → 클립 샘플링·TRS 보간 → Local Pose → 계층 누적 Global Pose → `Global × inverseBindPose` → 스키닝 팔레트 → GPU 업로드(상한 256본)

### 상하체 분리 블렌딩

기존 크로스페이드는 `elapsed / duration`으로 alpha를 올리다 1에 도달하면 스스로 해제된다. 두 클립을 계속 겹쳐 두는 구조가 아니라 상하체 분리에 쓸 수 없었다. 그래서 **마스크 레이어**를 별도 개념으로 추가했다.

| 항목 | 내용 |
| --- | --- |
| 구조 | 베이스 클립이 전신을 구동, 레이어 클립이 본 마스크 부위만 덮음 |
| 시간축 | 레이어는 독립 시간축으로 재생 (걷기 1.37초 / 던지기 2.20초가 각자 순환) |
| 가중치 | `LayerWeight`(0~1)로 레이어 세기 조절 → 상체 동작 페이드 인/아웃 |
| 재사용 | 마스크 가중 합성은 기존 `BlendLocalPoses`를 그대로 사용 (`weightedAlpha = alpha × mask[i]`, 새 블렌딩 수학 추가 없음) |

### 본 마스크 자동 분류

처음엔 UE 마네킹 본 이름을 하드코딩한 목록으로 상/하체를 갈랐다. 그런데 목록에 없는 본(`spine_04`, `neck_02`, `*_metacarpal_*`, `*_twist_02_*`)을 놓쳐서 **상체 마스크가 계층상 13조각으로 끊어져 있었다.** 부모와 자식은 마스크에 있는데 중간 본만 빠지면 블렌딩 시 그 지점이 꺾인다.

상체 루트의 **서브트리를 통째로** 잡는 계층 기반 분류로 바꿨다. 서브트리는 정의상 연결돼 있으므로 중간 누락이 구조적으로 불가능해진다. `ik_*`·`interaction`·`center_of_mass`처럼 스키닝 변형에 관여하지 않는 보조 본은 서브트리째 제외한다.

| | 수정 전 | 수정 후 |
| --- | --- | --- |
| 상체 마스크 연결성 | 13조각 | **단일 서브트리** |
| Quinn (91본) | 상체 47 / 하체 14 | **상체 62 / 하체 20** |
| Mixamo 리그 (66본) | 0 / 0 (분류 실패) | **상체 54 / 하체 12** |

### 검증

렌더링 없이 `.skelbin`을 직접 읽어 마스크 계층 정합성, 블렌딩 가중, 리타겟 오프셋을 검사하는 도구를 만들었다. 결과 **14 PASS / 1 FAIL**.

| 검증 항목 | 결과 |
| --- | --- |
| 마스크가 연결된 단일 서브트리, 상체 ∩ 하체 = 공집합 | PASS |
| `alpha=1` + 상체 마스크 → 상체 62본이 레이어를 100% 취하고 나머지는 베이스 유지 | PASS |
| 동일 스켈레톤 리타겟 → 항등 오프셋 | PASS (최대오차 **7.45e-08**) |
| 교차 리그 리타겟 | **FAIL** |

**한계** — 유일한 FAIL은 교차 리그 리타겟이다. `SetRetargetFromSkeletonHandles`가 두 스켈레톤을 **본 인덱스 순서로** 짝짓기 때문에, 리그가 다르면 이름이 어긋난다 (Quinn 91본 ↔ Mixamo 66본에서 이름 일치 0/66). decompose는 실패하지 않고 조용히 잘못된 값을 만든다. 유효 범위는 "본 순서가 같고 바인드 포즈만 다른 스켈레톤"이며, 제대로 하려면 인덱스가 아니라 본 이름으로 매칭해야 한다. 별도 작업으로 남겼다.

## 핵심 설계 5 — Behavior Tree

**적 AI**

FSM과 BT를 억지로 통합하지 않고 역할로 나눴다. **상태와 전이가 명확한 영역**(플레이어 행동, 애니메이션, 게임 Phase)은 FSM, **조건·우선순위·Running·Abort가 중요한 적 AI**는 BT.

| 항목 | 내용 |
| --- | --- |
| 노드 | Selector / Sequence / Parallel / Decorator / Task + Blackboard |
| 실행 | 모든 노드가 `Tick(ctx)`로 Success / Failure / Running 반환 |
| 재진입 | `Running`이면 active path를 유지하고 다음 Tick에 같은 노드부터 재진입 |
| 라이프사이클 | `OnEnter` / `OnTick` / `OnExit(status)` / `OnAbort`, Decorator Abort는 Tick 시작 시점 일괄 처리 |
| Blackboard | key별 version 관리 (값 변경 시에만 증가) |
| 메모리 | **트리 정의는 공유, 실행 상태만 인스턴스별 `memory[nodeId]`로 분리** → 여러 적이 하나의 트리를 공유 |

Blackboard 키는 `TargetActor`, `TargetDistance`, `TargetInSight`, `IsInCombat`, `IsMyTurn`, `CurrentHP`.
Task는 `MoveToTarget`, `RotateToTarget`, `StartAttack`, `ApplyAttackRoll`, `ApplyDamage`, `EndTurn`.

전투/비전투 트리를 분리하고 패트롤·접근·거리 유지·도주를 구현했다. PatrolPoint는 에디터에서 배치해 저장한다. AI 프레임워크 전체가 1.9k 라인이다.

## 트러블슈팅 1 — 바이너리 직렬화 시 컨테이너 덤프

**문제** — Mesh 데이터를 바이너리로 저장·로드하면 데이터가 깨지거나 로드 시 크래시.

**원인** — `std::vector`, `std::string`을 구조체째 덤프하면 내부 포인터가 함께 저장되어, 로드 시 무효 포인터를 읽는다.

**해결** — 포맷을 magic / version / count / offset / raw bytes / string(length + bytes)로 명시적으로 구성. Deserialize 시 파일 크기 대비 expected size 검증, 비정상적으로 큰 count 차단, 버전 불일치 검사 등 방어 코드 추가.

**결과** — 저장/로드 안정성 확보. 포맷 변경 시에도 version 검사로 하위 호환 문제를 조기 검출.

---

## 트러블슈팅 2 — 리소스 Handle을 파일에 저장하던 문제

**문제** — 씬을 저장 후 다시 로드하면 컴포넌트가 엉뚱한 리소스를 참조하거나 참조가 끊어짐.

**원인** — `ResourceHandle(id, generation)`은 실행마다 값이 달라지는 런타임 식별자인데, 이를 파일에 그대로 직렬화했다.

**해결** — 파일에는 key/path 같은 안정적인 참조만 저장하고, Deserialize 이후 resolve 단계에서 `ResourceStore`가 key를 handle로 복원(동일 key → 동일 handle 캐시). Mesh의 material 참조, Material의 texture 참조, Scene/Component의 리소스 참조에 동일 원칙 적용.

**결과** — 실행 세션과 무관하게 재현 가능한 저장 파일 확보.

---

## 트러블슈팅 3 — 임포터 드리프트

**코드가 에셋을 재현하지 못하던 문제**

포트폴리오를 정리하며 파이프라인을 재측정하다 발견했다.

**문제** — 현재 임포터 코드로 재임포트하니 Mixamo 리그의 본이 65개에서 198개로 3배 부풀었다.

**원인** — 에셋은 1월 커밋본이고 임포터 소스는 7월에 변경됐다. 그 사이 추가된 `CollectRequiredBoneNames`가 사용 본의 **모든 조상 노드**를 스켈레톤에 포함시키면서, Assimp의 FBX 피벗 헬퍼 노드(`_$AssimpFbx$_Translation` / `_PreRotation` / `_Rotation`)까지 본으로 들어왔다. 이 노드들이 애니메이션 채널도 쪼개고 있었다. **아무도 재임포트를 하지 않아 드러나지 않았다.**

**해결** — `AI_CONFIG_IMPORT_FBX_PRESERVE_PIVOTS`를 끄는 한 줄.

| | 커밋된 에셋 | 드리프트 | 수정 후 |
| --- | --- | --- | --- |
| Mixamo 리그 본 수 | 65 | 198 | **66** |
| 애니메이션 트랙 | 8 | — | **52** |
| 키프레임 | 336 | — | **2,184** |

**결과** — 65본 워크 사이클에 8트랙은 비정상이었다. 수정 후 팔·다리·척추가 모두 움직인다. 스키닝 없는 6개 에셋은 재임포트 결과가 **바이트 단위로 동일**해, 파이프라인이 결정적이며 이번 수정이 스키닝 에셋에만 영향을 준다는 것도 확인했다.

**교훈** — 에셋을 산출물로 커밋하면서 생성 코드와의 동기화를 검증하지 않으면 코드와 데이터가 조용히 갈라진다. 재현 가능한 임포트 도구와 검증 도구를 남긴 이유다.

---

## 트러블슈팅 4 — 좌표계 / 행렬 변환

**문제** — 임포트한 모델이 뒤집히거나, 노멀맵·컬링이 어긋나고, 본 트랜스폼이 이중 적용됨.

**원인** — Assimp(RH) → DX11(LH/Row-major) 변환 시 position만 변환하고 normal·tangent·winding/culling을 함께 맞추지 않음. `aiMatrix4x4` → `XMFLOAT4X4`를 memcpy로 옮기며 행/열 순서가 어긋남. 노드 트리의 local/global transform 누적이 중복 적용되는 경로 존재.

**해결** — 행렬은 원소를 명시적으로 옮기고, RH→LH 변환 시 normal/tangent/winding까지 일괄 처리. **좌표계 변환을 import 단계 한 곳에서만 수행하도록 규약을 고정**해 런타임은 항상 엔진 기준 데이터만 취급한다. 검증 케이스로 이동만 있는 큐브, Yaw 90° 큐브, 노멀맵 평면을 구성했다.

---

## 트러블슈팅 5 — UI 이벤트 증발

**문제** — 프레임(테두리) 이미지를 UI 위에 씌우면 그 아래 버튼들이 클릭 이벤트를 받지 못함.

**원인** — 최상위 UI가 이벤트를 가로채고 하위로 전달하지 않는 구조.

**해결** — 클릭 좌표 기준으로 해당 위치의 모든 UI 오브젝트에 이벤트를 전달하는 **위치 기반 라우팅**으로 변경. 각 컴포넌트가 자신이 처리할 이벤트인지 판단한다.

**결과** — 장식용 이미지와 상호작용 UI를 자유롭게 겹쳐 배치할 수 있다.

---

## 트러블슈팅 6 — 상태 전환 중 오브젝트 삭제 크래시

**문제** — 턴/FSM 상태 전환 도중 오브젝트를 즉시 삭제하면 순회 중인 컨테이너가 무효화되어 크래시.

**원인** — 이벤트 처리 중 씬 구조를 즉시 변경하는 재진입 문제.

**해결** — 삭제 요청을 `m_PendingRemovalNames`에 쌓고 프레임 끝에 `ProcessPendingRemovals()`로 일괄 처리하는 **지연(deferred) 방식**으로 변경.

### 아쉬운 점

**주장을 측정하지 않았다.** "런타임 의존성 제거", "상하체 독립 연출" 같은 항목을 구현 직후 확인만 하고 수치·검증으로 남기지 않았다. 나중에 재측정해보니 상체 마스크가 13조각으로 끊어져 있었고, 상하체 블렌딩은 호출부가 없어 실제로 동작하지 않는 상태였다. 지금은 재현 가능한 검증 도구를 만들어 뒀다.

**에셋과 생성 코드의 동기화를 검증하지 않았다.** 임포터를 고친 뒤 재임포트하지 않아 코드와 데이터가 조용히 갈라졌다. 산출물을 커밋하는 파이프라인이라면 "코드로 에셋을 재생성해 diff가 0인지" 확인하는 절차가 필요했다.

**나머지**

| 항목 | 내용 |
| --- | --- |
| 해상도 대응 | 일정 압박으로 포기하고 고정 해상도(2560×1600)로 제한했다 |

| 상태 전환 버그 | 후반에 몰아서 잡았다. 상태 다이어그램을 먼저 확정했다면 디버깅 비용이 줄었을 것이다 |
